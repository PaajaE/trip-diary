4. **Limity videa — částečně vyřešeno (2026-10-09).** `multipart-create` nově vyžaduje `durationMs` (celé číslo) a odmítá > 60 s (+ 500 ms tolerance na zaokrouhlení kontejneru): `invalid_duration`, `video_too_long` (400). Hodnotu deklaruje klient, API ji z velikosti souboru neověří; velikost dál omezuje `VIDEO_MAX_BYTES` (120 MB). Konstanty `VIDEO_MAX_DURATION_MS`, `VIDEO_DURATION_TOLERANCE_MS` jsou v `supabase/functions/_shared/media/upload.ts`; v1 konstanta `VIDEO_MAX_DURATION_SECONDS` (180 s, `packages/utils`) zůstává pro v1 kód a sjednotí se při odstranění v1. Zatím žádný klient `multipart-create` nevolá (T7); klient musí délku zjistit a poslat. Schéma DB limit nevynucuje (`media.duration_ms` bez omezení). Lokálně ověřeno proti běžící funkci: bez `durationMs` 400, 61 s 400, 60 s 200 (upload následně zrušen `multipart-abort`).

9. **Cache po smazání objektu (ověřeno 2026-10-09).** Po `delete-media` je objekt v R2 pryč (opakované mazání = 0), ale veřejná doména ho ještě servíruje z cache Cloudflare (`cf-cache-status: HIT`, 200); URL s jiným query vrací 404. 404 z domény mělo `cache-control: max-age=14400` (4 h u prohlížeče). **Okamžitá invalidace není zaručena** (kopie v prohlížečích nejdou smazat) a **zatím ji neimplementujeme** — rozhodnutí 2026-10-09: stávající chování cache se přijímá, bez purge a bez změny TTL. Možné budoucí řešení: purge podle URL po `delete-media` (nový secret + token jen s Cache Purge). Cache Rules a edge TTL zóny nebyly čteny (UNVERIFIED).
10. **Produkční JWT brána — UNVERIFIED.** Lokální test T3 běžel s `supabase functions serve --no-verify-jwt`, protože lokální brána odmítla uživatelský token (chyba verifikace JWT v edge runtime). Autentizaci tedy ověřila jen vlastní kontrola funkce (`auth.getUser()`); chování produkční brány (ověření JWT před funkcí, `verify_jwt` v `config.toml` není nastaveno) nebylo ověřeno.
11. **Změny časových pásem v tzdata (CI selhání PR #8, opraveno).** Test `zoneOffsetMinutes` očekával zimní offset `America/Edmonton` −420; CI (Node 24, novější tzdata 2026c) vrací −360, protože Alberta od 2026-11-01 zůstává trvale na −06. Lokální Node 22 má tzdata 2025b, proto test lokálně procházel. Test nyní používá `Europe/Prague`. Důsledek pro produkt: časové pásmo a offset z GPS závisí na tzdata běhového prostředí (`@photostructure/tz-lookup` + `Intl`); při ověřování fotek z Kanady po 2026-11-01 počítat s rozdílem mezi prostředími.
